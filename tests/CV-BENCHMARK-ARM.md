# OpenCV 在本机（ARM64）的实测耗时

> 2026-11-19。**这是实测，不是推测。** 之前所有关于 cv2 性能的数字都是【推测】，
> 直接影响「模坂匹配值不值得做」的判断，所以必须先测。

## 测试条件

- 设备：红魔 NX809J / Android 16 / proot Ubuntu
- 图：真实截图 **1592×720 RGBA**（虚拟屏横屏）
- Python 3.12 + opencv-python-headless 5.0.0.93
- 每个方法跑 N 次取中位数（冷缓存）

## 结果

| 方法 | 中位 | 最快 | 最慢 | 说明 |
|---|---|---|---|---|
| `import cv2` | **328ms** | — | — | **必须常驻进程**，否则每次都付这个 |
| dHash 64bit 指纹 | **7.0ms** | 7.0 | — | 缩到 9×8 再算差分 |
| 差分 MAD + maxCell（24×24）| **2.3ms** | 2.3 | 6.3 | 比 32×32 灰度还快 |
| **模板匹配 1/4 金字塔 + 精修** | **5.7ms** | 5.6 | 10.6 | 80×60 模板 |
| 模板匹配 全分辨率（对照）| **129ms** | 126 | 129 | 慢 23 倍 |
| 颜色 Lab + 连通域 | **6.8ms** | 4.6 | 165.7 | 偶发 165ms（GC？）|
| Canny | **0.7ms** | 0.6 | 3.4 | 非常快 |
| 缩放 1/4 | **0.2ms** | 0.2 | 2.2 | |

## 三个结论

### ① 模板匹配 5.7ms —— 比 OCR 快 280 倍

```
模板匹配:  5.7ms
OCR:       1600ms（冷）/ 500ms（缓存）
```

**这直接改变了架构判断**：找图标/开关/技能格这种「没有文字的东西」，
模板匹配是唯一可行的快速路径（OCR 根本读不到图形）。

### ② 金字塔是必须的，但全分辨率也没那么可怕

| | 耗时 | 倍数 |
|---|---|---|
| 金字塔+精修 | 5.7ms | 1× |
| 全分辨率 | 129ms | **23×** |

子代理担心「全图 matchTemplate 2-6 秒」—— 实测只要 129ms。
所以：
- **常规用金字塔**（5.7ms）
- **一次性精确搜索可以用全分辨率**（129ms 也能接受）

### ③ `import cv2` 328ms —— 必须常驻

如果每个工具调用都起一个新 Python 进程，光 import 就 328ms，
模板匹配从 5.7ms 变成 334ms（慢 58 倍）。

**所以必须有常驻的 `vision_helper.py`**（复用 `ocr.js` 已验证的 stdin/stdout JSON 行协议）。

## 对设计的影响

| 原本的估计 | 实测 | 影响 |
|---|---|---|
| 模板 ROI 8-15ms | **5.7ms** | 比预期好，可以更激进地用 |
| 模板全屏 40-90ms | **129ms** | 比预期差，但可接受 |
| 颜色 20-35ms | **6.8ms** | 比预期好 3-5 倍 |
| Canny 10-15ms | **0.7ms** | 好 14 倍 |
| dHash 1-3ms | **7.0ms** | 比预期慢，但仍可忽略 |
