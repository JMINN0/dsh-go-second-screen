# 无障碍树能不能读虚拟屏 —— **【不知道】，测试不足以判定**

> 2026-11-19 初测 + 同日复核修正。**原来写的「实测否证」是错的，已降级成【不知道】。** 原因见「为什么原来的否证不成立」。

## 曾经的想法

OCR 是我们最大的性能瓶颈（1.9-3.3 秒/次）。而 Android 的无障碍服务能直接拿到
控件的文字、坐标、可点击性 —— 理论上 50-100ms，是 OCR 的 20-30 倍。

如果无障碍树能读到「虚拟屏上的 App」，端到端能从 2-3 秒降到几百毫秒。

## 初测结果：读屏工具返回的是主屏

**注意：这只说明读屏工具的行为，不等于平台限制。**

**测试方法**：
1. 建虚拟屏 488（横屏 1592×720）
2. 把「设置」投到虚拟屏上（`am start --display 488 -n com.android.settings/.Settings`）
3. 调用无障碍通道读屏幕（`mcp__phone__screen`）

**返回**：
```
屏幕 s1 · 哔哩哔哩 · 横屏 · 键盘收起 · 共 1 项
  [1] 文本 哔哩哔哩的标题栏。
```

**读到的是主屏上正在播的 B 站视频，不是虚拟屏上的设置页。**

## 为什么原来的「否证」不成立（2026-11-19 复核）

上面那次测试**只证明了「DSH Go 的读屏工具读的是主屏当前活动窗口」**，
但它**没有排除**另外三种解释：

| 解释 | 可能性 | 说明 |
|---|---|---|
| **A. a11y 真的只覆盖主屏** | 可能 | 平台层限制 |
| **B. 读屏工具用的是 `getRootInActiveWindow()`** | **最可能** | 活动窗口语义。虚拟屏没有输入焦点 → 天然返回主屏 |
| **C. 读屏工具没请求 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS`** | 可能 | 没这个 flag 时 `getWindows()` 返回空列表 |

**B 最可能**：`mcp__phone__screen` 读的是「当前活动窗口」，而虚拟屏上的
App 从来没有输入焦点（`FLAG_OWN_FOCUS` 是为了不抢主屏焦点）。

而且 `LIMITS.md` 自己写着「虚拟屏上的无障碍树能不能读 —— **没试过**」，
和这份文档原来的「设计如此」直接矛盾。

**正确做法：按 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS` 写一个自定义无障碍服务，
直接 dump `getWindows()` 每一条的 type/bounds/package，看有没有虚拟屏的窗口。**

这条没做，所以结论只能是【不知道】。

## 这个结论否掉了什么

| 方案 | 状态 |
|---|---|
| 用无障碍树替代 OCR（20-30x 提速）| ❌ **对虚拟屏无效** |
| 无障碍 + 虚拟屏 = 又快又不打扰 | ❌ **不成立** |

## 但它也确认了什么

**两套方案是互补的，不是竞争的**：

| 能力 | 官方无障碍（`mcp__phone__*`）| 我们的虚拟屏 |
|---|---|---|
| 能看到虚拟屏上的 App | ❌ | ✅ |
| 能看到主屏 | ✅ | ❌（只能截图）|
| 读界面结构（按钮/输入框）| ✅ 快（~1s）| ❌ 只能 OCR |
| 读任意文字（canvas/游戏）| ❌ | ✅ |
| 打扰用户 | ✅ 会抢焦点/键盘 | ❌ 不会 |
| 操作游戏/自绘 UI | ❌ 基本不行 | ✅ |
| 多任务并行 | ❌ 一块屏 | ✅ 屏幕池 |

**所以正确的架构是「按场景选」**：
- 用户不在用手机 + 目标是普通 App → 用官方无障碍（快、准）
- 用户在用手机 / 目标是游戏 / 需要不打扰 → 用虚拟屏

## 怎么才能定论（两个测试）

### 测试 A（5 分钟，不改代码）
1. 虚拟屏起设置页
2. `dumpsys window displays | grep -E "mDisplayId=|mCurrentFocus"` 记下焦点
3. 往虚拟屏 tap 一下，再查焦点有没有切过去
4. 再调读屏工具

- 看到设置页 → 焦点假设成立，**原来的否证被推翻**
- 还是主屏 → **仍不能下结论**（可能只是没请求那个 flag）

⚠️ 会抢一次全局输入焦点，用户前台 App 可能被 pause，**要挑用户没在用手机时做**。

### 测试 B（1.5 小时，决定性）
在已有的 `com.dsh.overlay` 里加一个 `AccessibilityService`，
只做一件事：dump `getWindows()` 的每条信息到 logcat。

**不用新建 APK** —— 构建工具链齐，插件已能自动装。

**两个坑**：
1. `overlay/build.sh:32` 的 aapt **没有 `-S res`**，现在 APK 是零资源的。
   不加 `-S res` 就解析不到 `<meta-data>` → `canRetrieveWindowContent` 失效 →
   `window.getRoot()` 永远 null。**这个坑很隐蔽。**
2. `settings put secure enabled_accessibility_services` 必须**读改写**（冒号分隔）。
   覆盖写会弄掉 DSH Go 自己的无障碍服务 = **弄坏用户的手机操控**。
   本机当前是：`li.songe.gkd/...:cn.zte.aigcinput/...`（还有更多，已截断）

## 还剩的可能（未验证）

1. **自己写一个无障碍服务**，用 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS` 拿所有窗口
   - 能不能拿到虚拟屏的窗口？【不知道】需要实测
   - 但即使能，虚拟屏上的窗口可能本来就不在列表里（上面的推论）
2. **`AccessibilityWindowInfo.getDisplayId()`** —— 如果这个方法存在且能返回虚拟屏 id，
   说明窗口本来就在列表里，只是默认过滤掉了。【不知道】

**要彻底确认，需要一个带 FLAG_RETRIEVE_INTERACTIVE_WINDOWS 的自定义无障碍服务实测。**
这需要装 APK + 用户手动开启无障碍权限，成本比刚才那次测试高得多。
